# Аналитика: Умный кредитный кабинет предпринимателя

Аналитика команды: 20–21.10.2026, обновлена 25.10.2026.

> Документ написан до начала разработки и задавал требования к прототипу. Где реализация от него отличается и почему — в разделе [«Что изменилось при реализации»](#что-изменилось-при-реализации) в конце. Баллы, исходы демо-компаний и тестовые сценарии уже приведены к реализации.

## Резюме

Делаем веб-прототип кредитного конвейера: предприниматель за 10 минут подаёт заявку по ИНН и видит её путь до решения, а банк обрабатывает её в одной системе — автоматически или руками аналитика.

**Проблема клиента.** Предприниматель не знает, какой продукт ему подходит, заполняет одни и те же данные несколько раз и не понимает, что происходит с заявкой после отправки.

**Проблема банка.** Заявки приходят неполными, данные о компании приходится собирать вручную, нестандартные случаи теряются в общей очереди.

**Наше решение в трёх тезисах:**

1. **Подбор продукта по задаче, а не по названию.** Клиент отвечает «для чего деньги», система предлагает продукт и показывает примерный платёж.
2. **Автозаполнение по ИНН.** Данные о компании подтягиваются из ЕГРЮЛ/ЕГРИП (мок), клиент только проверяет и дополняет финансы.
3. **Прозрачный конвейер.** Каждая смена статуса видна клиенту с объяснением простым языком. Решение — не только «да/нет»: есть контрпредложение и запрос документов. Аналитик видит разбор скоринга по факторам.

**Метрики успеха прототипа:** время подачи заявки ≤ 10 минут; доля заявок с автоматическим решением ≥ 60% на тестовом наборе; у каждого статуса есть понятное клиенту объяснение и следующее действие.

> Все цифры по ставкам, лимитам и весам скоринга ниже — условные, для прототипа. Это явно описанное упрощение, разрешённое кейсом (ограничение 06).

## Пользователи

Главный пользователь — владелец микробизнеса без финансового образования; ради него упрощаем язык и автозаполняем данные. Остальные роли получают то же, но с большим контролем деталей.

### Jobs To Be Done

- **Когда** у бизнеса появляется расход, на который не хватает своих денег, **я хочу** быстро понять, сколько и на каких условиях мне дадут, **чтобы** принять решение о покупке без риска для бизнеса.
- **Когда** я отправил заявку, **я хочу** видеть, что с ней происходит и что от меня нужно, **чтобы** не звонить в банк и не терять время.
- **Когда** банк не готов дать то, что я просил, **я хочу** получить альтернативу, **чтобы** всё-таки решить задачу, а не начинать заново.
- **Когда** я аналитик и получил пограничную заявку, **я хочу** видеть все данные и причины оценки на одном экране, **чтобы** принять обоснованное решение за минуты.

| --- | --- | --- |

| Аналитик собирает данные руками | Банк | Обогащение данных и скоринг до того, как заявка попадёт к человеку |

## Границы MVP

В MVP входит один сквозной путь: от выбора продукта до симуляции выдачи, для двух ролей (клиент и аналитик) и трёх продуктов. Всё, что не нужно для этого пути, откладываем.

**Граница процесса:** начинается с выбора цели финансирования в кабинете, заканчивается статусом «Средства выданы» (симуляция зачисления). Обслуживание кредита, график погашения после выдачи, залоги и поручительства — за границей.

| Функция | MoSCoW | Почему |
| --- | --- | --- |
| Регистрация/вход клиента и аналитика (тестовые аккаунты) | Must | Без ролей нет двух сторон процесса |
| Подбор продукта по цели + калькулятор платежа | Must | Закрывает главную боль «не знаю, что выбрать» |
| Анкета заявки с автозаполнением по ИНН | Must | Снижает повторный ввод, ключевой UX-аргумент |
| Проверка полноты и корректности данных | Must | Явный этап конвейера из кейса |
| Моки ЕГРЮЛ/ЕГРИП и БКИ | Must | Обогащение данных, требование кейса |
| Балльный скоринг с объяснением факторов | Must | Ядро модели принятия решения |
| Кредитная логика: одобрение / контрпредложение / дозапрос / отказ / ручное рассмотрение | Must | Кейс прямо говорит, что итог не бинарный |
| Кабинет аналитика: очередь, карточка, решение | Must | Банковская сторона процесса |
| Таймлайн статусов с объяснением для клиента | Must | Прозрачность — критерий оценки |
| История статусов и аудит-лог | Must | Enterprise-ориентированность |
| Дозапрос документов и загрузка в кабинете | Should | Сценарий «нужна доп. информация» |
| Подписание договора (симуляция ПЭП кодом) и выдача | Should | Завершает путь до результата |
| Уведомления внутри кабинета (колокольчик) | Should | Email/SMS запрещены, нужна замена |
| ИИ-помощник подбора продукта (open-weights LLM) | Could | Ценность есть, но не критична; только если ядро готово к 23.10 |
| Распознавание отчётности из PDF | Could | Красиво, но рискованно по срокам |
| Роль риск-менеджера/руководителя, лимиты полномочий | Won't | Усложняет без пользы для демо |
| Залоги, поручительства, гарантии | Won't | Отдельный большой процесс |
| Реальные интеграции, платежи, ЭЦП | Won't | Запрещено условиями, только моки |

**Правило приоритета:** до вечера 22 октября делаем только Must. Should — 23–24 октября. Could — только если сквозной путь уже стабильно проходит.

## Роли и пользовательские сценарии

В системе три участника: клиент, аналитик и автоматический конвейер (system). Конвейер делает всё, что можно сделать без человека, аналитик подключается только к пограничным случаям.

| Роль | Права | Что делает |
| --- | --- | --- |
| `CLIENT` | Видит только заявки своей компании | Выбирает продукт, создаёт и отправляет заявку, догружает документы, принимает/отклоняет контрпредложение, подписывает договор |
| `ANALYST` | Видит все заявки в статусе ручного рассмотрения и историю любых заявок | Берёт заявку в работу, запрашивает документы, одобряет / делает контрпредложение / отказывает с комментарием |
| `SYSTEM` | Технический исполнитель | Проверяет полноту, вызывает моки, считает скоринг, применяет правила решения, меняет статусы |

### Ключевые user stories (для бэклога)

1. Как клиент, я хочу выбрать цель финансирования и сразу увидеть подходящий продукт с примерным платежом, чтобы понять, потяну ли я кредит.
2. Как клиент, я хочу ввести только ИНН и получить заполненные данные компании, чтобы не перепечатывать реквизиты.
3. Как клиент, я хочу, чтобы черновик сохранялся, чтобы вернуться к заявке позже.
4. Как клиент, я хочу видеть текущий этап заявки и что от меня нужно, чтобы не звонить в банк.
5. Как клиент, я хочу получить альтернативные условия вместо отказа, если это возможно.
6. Как клиент, я хочу загрузить запрошенный документ в кабинете и продолжить с того же места.
7. Как аналитик, я хочу видеть очередь заявок с приоритетом и сроком, чтобы разбирать важные первыми.
8. Как аналитик, я хочу видеть разбор скоринга по факторам и данные из внешних источников на одной странице.
9. Как аналитик, я хочу одобрить, изменить условия, запросить документ или отказать с обязательным комментарием.
10. Как банк, я хочу, чтобы каждое изменение заявки фиксировалось в журнале с автором и временем.

### Расчёт платежа

Для аннуитетных продуктов калькулятор и договор считают платёж по стандартной формуле, где S — сумма, i — месячная ставка (годовая / 12 / 100), n — срок в месяцах:

```math
P = S \cdot \frac{i (1 + i)^n}{(1 + i)^n - 1}
```

Для овердрафта показываем проценты за месяц при полном использовании лимита: S × годовая ставка / 12 / 100.

## Статусная модель заявки

У заявки 14 статусов, 4 из них финальные: «Средства выданы», «Отказ», «Отозвана», «Истекла». Переходы разрешены только по таблице ниже — бэкенд отклоняет любой другой переход с ошибкой `409 INVALID_TRANSITION`.

Диаграмма состояний и полная таблица переходов, как они реализованы, — в [state-machine.md](state-machine.md).

Стоп-факторы на этапе проверки компании ведут в «Отказ» по стрелке «авто»: система решает без аналитика. Пограничные заявки и суммы выше лимита авто-решения уходят к аналитику.

| Из | В | Триггер | Кто |
| --- | --- | --- | --- |

| `ENRICHMENT` | `SCORING` | Данные получены | Система |
| `ENRICHMENT` | `REJECTED` | Стоп-фактор: компания ликвидирована / в банкротстве | Система |

| `MANUAL_REVIEW` | `INFO_REQUESTED` | Аналитик запросил документ | Аналитик |
| `APPROVED` | `SIGNING` | Клиент принял условия | Клиент |
| `COUNTER_OFFER` | `SIGNING` | Клиент принял новые условия | Клиент |
| `COUNTER_OFFER` | `CANCELLED` | Клиент отклонил предложение | Клиент |
| `SIGNING` | `ISSUED` | Код ПЭП введён верно, зачисление выполнено | Клиент → Система |
| Любой нефинальный до `SIGNING` | `CANCELLED` | Клиент отозвал заявку | Клиент |
| `INFO_REQUESTED`, `APPROVED`, `COUNTER_OFFER` | `EXPIRED` | Нет ответа 7 дней (в демо — кнопка «Промотать время» у аналитика) | Система |

**Правила реализации:**

- Переход — одна транзакция: смена статуса + запись в `status_history` + событие в `audit_log` + уведомление клиенту.
- Автоматические этапы (`SUBMITTED` → … → решение) выполняются фоново за 3–5 секунд; в демо добавляем искусственную задержку \~1 с на этап, чтобы клиент видел движение по таймлайну.
- Каждый статус хранит текст для клиента и «следующее действие» — их рисует фронт, не придумывает сам.

## Скоринг и кредитная логика

Решение принимается в три шага: стоп-факторы → балльный скоринг → кредитные правила. Скоринг отвечает «насколько рискованно», правила — «что предложить». Так одинаковый балл даёт разные условия для разных продуктов, как и требует кейс.

### Шаг 1. Стоп-факторы (сразу отказ)

| Код | Условие | Источник | Причина для клиента |
| --- | --- | --- | --- |
| `SF_COMPANY_INACTIVE` | Статус компании «ликвидирована», «в процессе ликвидации», «банкротство» | ЕГРЮЛ/ЕГРИП | Компания не ведёт деятельность по данным реестра |
| `SF_CURRENT_DELINQUENCY` | Текущая просрочка > 90 дней | БКИ | Есть непогашенная длительная просрочка по другим кредитам |
| `SF_TOO_YOUNG` | Возраст бизнеса меньше минимума продукта | ЕГРЮЛ/ЕГРИП | Бизнес работает меньше, чем требуется для продукта |

### Шаг 2. Балльный скоринг

Стартовый балл — 600. Каждый фактор прибавляет или отнимает баллы, итог ограничен диапазоном 0–1000. Все веса лежат в конфиге `scoring_rules`, не в коде.

| Фактор | Условие → баллы | Источник |
| --- | --- | --- |
| Возраст бизнеса | < 12 мес: −60 · 12–36 мес: 0 · > 36 мес: +40 | ЕГРЮЛ/ЕГРИП |
| Динамика выручки (последние 6 мес к предыдущим 6) | рост > 10%: +40 · ±10%: 0 · падение 10–20%: −40 · падение > 20%: −80 | Анкета |
| Долговая нагрузка DTI = (текущие платежи + новый платёж) / средняя мес. выручка | < 10%: +60 · 10–20%: 0 · 20–25%: −60 · > 25%: −150 | Анкета + БКИ |
| Просрочки за 12 мес | нет: +60 · до 30 дней: −50 · 31–90 дней: −150 | БКИ |
| Кредитная история | есть закрытые кредиты без просрочек: +40 · истории нет: 0 | БКИ |
| Запросы в БКИ за 30 дней | > 3: −40 · иначе: 0 | БКИ |
| Отраслевой риск по ОКВЭД | низкий: 0 · средний: −20 · высокий: −40 | ЕГРЮЛ + справочник |
| Налоговая задолженность | есть: −60 · нет: 0 | Мок «Прозрачный бизнес» |

**Рейтинг по баллу:**

| Рейтинг | Балл | Риск | Поправка к ставке |
| --- | --- | --- | --- |
| A | ≥ 700 | Низкий | −1 п.п. |
| B | 600–699 | Умеренный | 0 |
| C | 500–599 | Пограничный | +2 п.п. |
| D | < 500 | Высокий | — (отказ) |

### Шаг 3. Кредитные правила

Сначала считаем максимально доступную сумму: минимум из максимума продукта, лимита от выручки (см. «Кредитные продукты») и суммы, при которой DTI не превышает 25%.

1. Есть стоп-фактор → `REJECTED`.
2. Рейтинг D → `REJECTED` с топ-3 факторами, снизившими балл.
3. Рейтинг C → `MANUAL_REVIEW`.
4. Рейтинг A/B и запрошенная сумма > доступной:
   1. Доступная ≥ минимума продукта → `COUNTER_OFFER`: доступная сумма; если увеличение срока в пределах продукта помещает DTI в 25% — предлагаем запрошенную сумму на больший срок.
   2. Доступная < минимума продукта → `REJECTED`.
5. Рейтинг A/B, сумма в доступной, но выше лимита авто-решения продукта → `MANUAL_REVIEW`.
6. Иначе → `APPROVED` со ставкой = базовая + поправка рейтинга.

### Что сохраняем по каждой оценке

Запись `scoring_result`: балл, рейтинг, список факторов (код, значение, баллы, текст для аналитика, текст для клиента), стоп-факторы, доступная сумма, рекомендованное решение, версия правил. Версия правил нужна, чтобы любое решение можно было воспроизвести — это аргумент про enterprise и аудит.

**Пример объяснения клиенту** (ответ прототипа для «Хлебного дома»): «Не можем одобрить 900 000 ₽ на 24 мес: платежи по другим кредитам уже занимают 20% выручки». Варианты под 15%: 900 000 ₽ на 30 мес с платежом ≈ 36 160 ₽ в месяц или 820 000 ₽ на 24 мес с платежом ≈ 39 760 ₽.

> Почему не ML: на синтетических данных модель ничего не докажет, а балльная карта прозрачна, объяснима и проверяема. В разделе «Развитие» описываем, как заменить карту на модель без изменения конвейера.

## Внешние интеграции (моки)

Все внешние системы — один сервис `mock-external` с отдельными эндпоинтами и данными из seed-файла, привязанными к ИНН. Конвейер ходит в него через клиентов-адаптеров с таймаутом 3 с и одним повтором, поэтому замена мока на реальную интеграцию — это замена адаптера.

| Мок | Реальный прототип | Эндпоинт мока | Возвращает | Когда вызывается |
| --- | --- | --- | --- | --- |
| Реестр компаний | ЕГРЮЛ / ЕГРИП (ФНС) | `GET /registry/{inn}` | Наименование, ОГРН/ОГРНИП, тип (ЮЛ/ИП), статус, дата регистрации, адрес, ОКВЭД основной, руководитель | Автозаполнение анкеты по ИНН; повторно на `ENRICHMENT` |
| Прозрачный бизнес | Сервис ФНС «Прозрачный бизнес» | `GET /tax/{inn}` | Наличие налоговой задолженности, среднесписочная численность, спецрежим | `ENRICHMENT` |
| Бюро кредитных историй | НБКИ / ОКБ и др. | `POST /bki/report` (inn, согласие) | Действующие кредиты (сумма, ежемес. платёж), закрытые кредиты, просрочки за 12 мес (макс. дней), текущая просрочка, запросы за 30 дней | `ENRICHMENT`, только при наличии согласия |
| Подписание | ПЭП по коду | `POST /sign/request`, `POST /sign/confirm` | Код подтверждения (в демо показывается на экране, не по SMS) | `SIGNING` |
| Выдача | АБС банка | `POST /payout` | ID операции, дата зачисления | `SIGNING` → `ISSUED` |

**Поведение для демо:**

- Неизвестный ИНН → `404`, клиент вводит данные вручную (проверяем ручную ветку).
- Специальный ИНН `0000000000` → мок отвечает `503`, конвейер делает повтор и показывает аналитику ошибку интеграции — демонстрирует отказоустойчивость.
- Код ПЭП в демо всегда отображается на экране подписания: SMS запрещены условиями, а сценарий должен проходиться внутри продукта.

**Согласие на запрос в БКИ** — обязательный чекбокс перед отправкой заявки; без него `POST /applications/{id}/submit` возвращает `422`. Факт и время согласия пишем в заявку.

## Модель данных

Центральная сущность — `application` (заявка); всё остальное либо описывает её участников (пользователь, компания, продукт), либо фиксирует её историю (статусы, оценки, решения, документы, аудит). Суммы храним в копейках (`bigint`), даты — в UTC, идентификаторы — UUID.

| Таблица | Ключевые поля | Связи |
| --- | --- | --- |
| `users` | id, email, password\_hash, full\_name, role (`CLIENT` / `ANALYST`), created\_at | — |
| `companies` | id, inn (уникальный), ogrn, type (`LLC` / `IE`), name, status, registered\_at, okved, address, director\_name | — |
| `company_members` | user\_id, company\_id, position (`OWNER`, `CEO`, `CFO`, `ACCOUNTANT`, `OTHER`) | users ↔ companies, многие-ко-многим |
| `company_financials` | id, company\_id, period\_month, revenue, expenses, existing\_monthly\_payments, source (`CLIENT` / `DOCUMENT`) | companies 1 → N |
| `products` | id, code, name, purpose\_tags, min\_amount, max\_amount, min\_term, max\_term, base\_rate, revenue\_multiplier, min\_business\_age\_months, auto\_decision\_limit, required\_docs, is\_active | — |
| `applications` | id, number (`ЗК-2026-000123`), company\_id, applicant\_id, product\_id, purpose, requested\_amount, requested\_term, status, bki\_consent\_at, submitted\_at, decided\_at, version | companies, users, products |
| `application_status_history` | id, application\_id, from\_status, to\_status, actor\_type (`CLIENT` / `ANALYST` / `SYSTEM`), actor\_id, reason, created\_at | applications 1 → N |
| `external_checks` | id, application\_id, source (`REGISTRY` / `TAX` / `BKI`), request\_payload, response\_payload (jsonb), status (`OK` / `ERROR`), duration\_ms, created\_at | applications 1 → N |
| `scoring_results` | id, application\_id, score, grade, factors (jsonb), stop\_factors (jsonb), max\_available\_amount, recommended\_decision, rules\_version, created\_at | applications 1 → N |
| `decisions` | id, application\_id, type (`APPROVE` / `COUNTER_OFFER` / `REJECT` / `REQUEST_INFO`), amount, term, rate, monthly\_payment, product\_id, reasons (jsonb), comment, decided\_by (`SYSTEM` / user\_id), created\_at | applications 1 → N |
| `info_requests` | id, application\_id, doc\_type, message, status (`OPEN` / `FULFILLED`), requested\_by, created\_at, fulfilled\_at | applications 1 → N |
| `documents` | id, application\_id, info\_request\_id?, doc\_type, file\_name, mime, size, storage\_key, uploaded\_by, created\_at | applications 1 → N |
| `contracts` | id, application\_id, decision\_id, body\_html, sign\_code\_hash, signed\_at, payout\_id, issued\_at | applications 1 → 1 |
| `notifications` | id, user\_id, application\_id, title, text, is\_read, created\_at | users 1 → N |
| `audit_log` | id, entity\_type, entity\_id, action, actor\_id, before (jsonb), after (jsonb), ip, created\_at | — (только запись) |
| `scoring_rules` | version, config (jsonb), is\_active, created\_at | — |

**Важные инварианты:**

- `applications.status` меняется только сервисом машины состояний; поле `version` — оптимистическая блокировка от двойных кликов и гонок.
- Действующее решение заявки — последняя запись `decisions`; старые не удаляются.
- `audit_log` и `application_status_history` — только `INSERT`, без `UPDATE`/`DELETE`.
- Персональные данные (ФИО, контакты) отдаём аналитику, но не пишем в логи приложения.

### Тексты решений для клиента

- **Одобрено:** «Готовы выдать 1 500 000 ₽ на 24 месяца под 17% годовых. Платёж — 74 200 ₽ в месяц. Подтвердите условия, чтобы перейти к подписанию.»
- **Контрпредложение:** «Не можем одобрить всю сумму, но можем предложить другие условия» + сравнение «Вы запросили / Мы предлагаем» + одна главная причина.

- **Отказ:** «К сожалению, сейчас мы не можем выдать кредит. Основные причины: …» + «Что можно сделать: повторить заявку через 3 месяца / выбрать меньшую сумму».
- **Ручное рассмотрение:** «Вашу заявку изучает специалист. Обычно это занимает до 1 рабочего дня. Мы сообщим здесь, если что-то понадобится.»

### Сквозные тестовые сценарии (E2E)

| # | Сценарий | Шаги | Ожидаемый результат |
| --- | --- | --- | --- |
| T1 | Счастливый путь | igor → цель «Закупить товар» → ИНН → финансы → отправить → принять → подписать кодом | Статусы проходят до `ISSUED`, таймлайн показывает все этапы |
| T2 | Дозапрос документа | anna → оборудование без счёта → загрузить счёт | `INFO_REQUESTED` → `VALIDATION` → … → `APPROVED` |
| T3 | Контрпредложение | olga за «Хлебный дом» → принять вариант 820 тыс. на 24 мес → подписать | `COUNTER_OFFER` → `SIGNING` → `ISSUED`, в договоре 820 тыс. на 24 мес |
| T4 | Отказ от контрпредложения | То же, нажать «Отклонить» | `CANCELLED` |
| T5 | Ручное рассмотрение | olga за «СтройМастер» → analyst предлагает 1 млн с комментарием | Клиент видит контрпредложение от специалиста |
| T6 | Запрос аналитика | olga за «Агротех» → analyst запрашивает отчётность → olga загружает → analyst одобряет | Цикл `MANUAL_REVIEW` → `INFO_REQUESTED` → … → `APPROVED` |
| T7 | Отказ по скорингу | kozlov за ИП Козлов | `REJECTED`, видны 3 главные причины |
| T8 | Стоп-фактор | kozlov за «Ромашку» | `REJECTED` по стоп-фактору |
| T9 | Сбой интеграции | Остановить mock-external и отправить заявку; поиск по ИНН 0000000000 отвечает 503 | Повтор, затем MANUAL\_REVIEW: ошибка видна аналитику, клиент видит «Заявку рассматривает специалист» |
| T10 | Недопустимый переход | `POST /applications/{id}/accept` для заявки в `DRAFT` | `409 INVALID_TRANSITION` |
| T11 | Права доступа | anna открывает заявку igor по ID | `403` |
| T12 | Истечение срока | В прототипе не реализовано: таймера нет | `EXPIRED` (переход есть в модели статусов) |
| T13 | Без согласия на БКИ | Отправить без чекбокса | `422`, заявка остаётся в `DRAFT` |

T1, T3, T5 и T7 показывают четыре исхода конвейера за 5 минут — с них удобно начать знакомство с продуктом: [demo.md](demo.md). Как проверяется каждый сценарий — [test-scenarios.md](test-scenarios.md).

## Нефункциональные требования, риски, развитие

Критерий «Enterprise-ориентированность» закрываем конкретными механизмами, а не словами: каждый пункт ниже должен быть виден в коде или README.

### Нефункциональные требования

| Область | Что делаем в прототипе |
| --- | --- |
| Безопасность | JWT с коротким сроком жизни, хэш паролей bcrypt/argon2, проверка прав на уровне заявки (клиент видит только свои компании), валидация входных данных, лимит размера и типа файлов, секреты только через `.env` |
| Надёжность | Машина состояний с оптимистической блокировкой, идемпотентные ручки, транзакционная смена статуса, таймауты и повтор при вызове моков |
| Отказоустойчивость | Сбой внешнего сервиса не роняет заявку: статус остаётся, ошибка видна аналитику, есть повторный запуск (`/rescore`) |
| Масштабирование | Stateless API за балансировщиком; этапы конвейера — фоновые задачи из очереди, которые можно вынести в отдельные воркеры |
| Сопровождение | OpenAPI из кода, миграции БД, конфиг продуктов и скоринга в данных, структурированные логи с `application_id`, health-check эндпоинты, тесты на машину состояний и скоринг |
| Воспроизводимость | `docker compose up` поднимает всё: фронт, API, БД, моки, seed-данные; версии зафиксированы lock-файлами |
| Аудит | `audit_log` и `application_status_history` — только на запись; версия правил скоринга в каждом решении |

### Риски

| Риск | Вероятность | Что делаем |
| --- | --- | --- |
| Не успеваем собрать сквозной путь | Средняя | До 22.10 вечером только Must; «тонкий» путь раньше красивого UI |
| Расхождение фронта и бэка | Средняя | Контракт API фиксируем 21.10 утром, фронт работает на моках по нему |
| Проект не запускается у жюри | Средняя | Прогон `docker compose up` с чистой машины 25–26.10, seed запускается автоматически |
| ИИ-фича съедает время | Высокая | Только Could, старт не раньше 23.10 и только при стабильном ядре |
| Неясное требование про «новостную ленту» на слайде 7 | — | Спросить организаторов; если нужно — лента уведомлений по заявкам клиента |

### Развитие после хакатона

- Замена балльной карты на статистическую или ML-модель: интерфейс скоринга (вход — данные заявки, выход — балл и факторы) не меняется.
- Реальные интеграции с ЕГРЮЛ, БКИ, ЭЦП через существующие адаптеры.
- Новые продукты (гарантии, лизинг) — новые записи в `products` и правила.
- Роли руководителя и риск-менеджера с лимитами полномочий.
- Предодобренные предложения по данным расчётного счёта клиента в банке.
- Распознавание отчётности и ИИ-помощник на модели с открытыми весами.

## Что изменилось при реализации

Ядро осталось как в аналитике: три продукта с теми же параметрами, 14 статусов и переходы между ними, три шага решения (стоп-факторы → баллы → кредитные правила), моки внешних систем, два кабинета. Ниже — что сделали иначе или не сделали.

| Тема | В аналитике | В прототипе |
|---|---|---|
| Долговая нагрузка в скоринге | DTI с учётом нового платежа | В баллах — только текущие платежи к выручке. Новый платёж проверяют кредитные правила: вместе с ним платежи не больше 25% выручки. Поэтому баллы демо-компаний выше первой оценки (у «Хлебного дома» 760 вместо 630); таблица компаний выше уже обновлена |
| Стоп-факторы | Отказ на этапе `ENRICHMENT` | Проверяются вместе со скорингом, отказ — на `SCORING` |
| Веса скоринга | Конфиг `scoring_rules` в базе | Код пакета `@alfa/scoring` с тестами; версия правил записывается в каждый результат оценки |
| Подписание | `/sign/request` и `/sign/confirm` | Код выдаётся при принятии предложения (`POST /applications/{id}/accept`), подпись — `POST /applications/{id}/sign` |
| Ответ на предложение | `/offer/accept`, `/offer/decline` | `POST /applications/{id}/accept` с номером варианта; отказ — `POST /applications/{id}/cancel` |
| Кабинет аналитика | `/analyst/queue`, `/info-request`, `/assign`, `/rescore` | `GET /analyst/applications`, `POST /analyst/applications/{id}/request-info`. «Взять в работу» и ручного пересчёта нет: после загрузки документа конвейер сам проводит заявку заново |
| Данные компании | `POST /companies`, `PUT /financials`, правка черновика | Компании и финансы — из демо-данных; поиск по ИНН — `GET /registry/lookup` |
| Статус в реальном времени | SSE-поток и уведомления в кабинете | Кабинет опрашивает `GET /applications/{id}`: в ответе статус, текст для клиента и следующее действие. Уведомлений нет |
| Истечение срока | Таймер 7 дней и `/demo/time-travel` | Переходы в `EXPIRED` есть в модели, таймера нет |
| Защита от повторов | Заголовок `Idempotency-Key` | Оптимистическая блокировка по `version` и проверка статуса: второй такой же запрос получает `409`. Если после подписи сорвалась выдача, повтор не подписывает договор второй раз |
| Модель данных | Есть `notifications`, `audit_log`, `scoring_rules` | Этих таблиц нет. История — `application_status_history` (только запись), ответы внешних систем — `external_checks`. Схема — в [data-model.md](data-model.md) |
| Документы | Файловое хранилище, `storage_key` | Файлы в PostgreSQL: PDF, JPG или PNG до 10 МБ |
| Договор | HTML-документ | Запись с номером и принятыми условиями, без HTML/PDF-версии |
| OpenAPI | Генерируется из кода | Написан вручную и сверен с работающим API: все пути совпадают, ответы проверены по схемам |
| Конвейер | Фоновые задачи из очереди | Работает в процессе API, без очереди; после перезапуска продолжает заявки с того же этапа |
| Could-функции | ИИ-помощник, распознавание отчётности | Не делали; модели ИИ не используются |
